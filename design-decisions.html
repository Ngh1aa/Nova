Reading rule

Evidence before certainty.

Research signals and implementation proof are kept separate. QA shows that the prototype behaves as intended; it does not prove that people understand it better.

The three stories

Each story follows the same scan: problem → decision → rejected alternative → trade-off → evidence → remaining uncertainty.

01 · Protected money

Safe to spend only works if “protected” keeps one meaning.

Problem / constraint. A raw balance answers how much money exists, but not how much is safe after near-term commitments. Round 02 also showed that users could follow transfer arithmetic while still misunderstanding what the protected buffer did.

User self-report Prototype / technical
See Home See transfer decision

Decision

Lead with Safe to spend + a 14-day Money Horizon, then state at the transfer decision point that the protected buffer stays reserved and is not used by the transfer.

Rejected alternative

  • Raw balance as the hero
  • Automatically consume the buffer
  • Hide the reserve rule inside arithmetic

Trade-off

The model is more conservative and needs more explanation, but “protected” keeps a stable meaning across planning and payment.

Evidence

Round 02 D-03: 5/5 reached the transfer arithmetic, while only 1/5 correctly described buffer behavior. The follow-up copy and 14-day clarity changes are implemented and regression-checked.

Remaining uncertainty

The post-Round-02 clarity changes have not been human-retested, so Nova does not claim comprehension improved.

02 · Sensitive actions

Freeze and Report should not collapse into one vague “protect me” action.

Problem / constraint. In a suspicious-payment flow, speed matters, but the two actions create different consequences. The prototype also cannot imply that a real bank case was created.

User self-report Prototype / technical
See transaction detail See report preview

Decision

Separate Freeze and Report, explain each consequence beside the action, and place DEMO ONLY · NO BANK CONTACT at the decision/result surface.

Rejected alternative

  • Combined “Freeze / Report” control
  • Bank-contact implication
  • Footer-only prototype disclaimer

Trade-off

The surface is denser and asks for a little more reading, in exchange for clearer consequences at a high-risk moment.

Evidence

Round 02 D-02 stayed mixed: 3/5 responses still indicated real-bank consequence, uncertainty or action conflation. The follow-up truth boundary is now regression-protected.

Remaining uncertainty

The latest Freeze/Report version has not been human-retested. Implementation correctness is not evidence of improved understanding.

03 · Failure recovery

Before “Try again”, answer the scarier question: did my money move?

Problem / constraint. After biometric, network or revalidation failure, a generic error leaves transaction state ambiguous. Recovery must restore certainty before optimizing speed.

User self-report Prototype / technical
See biometric recovery See offline recovery

Decision

Make NO MONEY MOVED dominant, keep the concrete failure cause adjacent, state that balance is unchanged, and make retry/passcode actions secondary.

Rejected alternative

  • Generic error + Retry first
  • Silent resend after reconnect
  • Ambiguous completion state

Trade-off

Recovery is slightly slower, but transaction-state certainty is established before another high-consequence action can happen.

Evidence

Round 02 D-04 produced a negative cross-sectional self-report signal. That signal changed the hierarchy; it is not treated as causal proof.

Remaining uncertainty

The revised recovery hierarchy is implemented and QA-verified but not human-retested, so task-success or confidence improvement is unknown.

Evidence boundary

Supported

  • The three stories are traceable to retained self-report evidence, implementation and QA history.
  • Round 02 changed the priority of the money-model, sensitive-action and recovery problems.
  • The latest prototype changes are implemented and technically verified.

Not supported yet

  • Improved post-Round-02 comprehension or task success.
  • Moderated usability findings.
  • Conversion, retention, fraud reduction or production banking impact.
